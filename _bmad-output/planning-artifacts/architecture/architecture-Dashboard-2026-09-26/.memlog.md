- (constraint) SQLite is the database (user decision 2026-09-26)
- (constraint) Brownfield: Next.js 16.3.6 App Router, React 19.2.8, TS, Tailwind 4, shadcn/ui radix-nova, next-themes, Recharts, lucide; shell and design from story 1.5; URL-driven server table pattern from story 1.4
- (decision) Working mode: Fast path; deliverable: spine only (user)
- (decision) Paradigm: modular monolith, layered per module (UI -> actions/route handlers -> module service -> repository/db); modules own their tables; cross-module calls only via the other module's service API. Prevents two features writing the same table differently
- (decision) ORM/driver: Drizzle ORM 0.45.3 + better-sqlite3 13.0.3 (synchronous driver, BEGIN IMMEDIATE transactions); drizzle-kit migrations are the only schema-change path. Alternatives weighed: node:sqlite built-in (no drizzle driver in 0.45 exports), libsql (adds a server/remote layer not needed), Prisma (heavier, less control of transactions)
- (decision) SQLite implies a single long-running Node server process (next start), not serverless; WAL mode, busy_timeout, foreign_keys ON. Resolves PRD open question 4 partially: self-hosted single server (hospital server or single VM)
- (decision) Auth: Better Auth 1.7.6 with Drizzle adapter and admin plugin (roles, ban/unban); username+password, DB sessions; idle timeout 15 min; lockout after 5 failures (custom hook if the plugin lacks it). Alternatives: Auth.js v5 (credentials provider discourages DB sessions), hand-rolled jose sessions (more security surface)
- (decision) Authorization: one permission map (role x action) in src/server/auth/permissions.ts mirrors the PRD FR-2 matrix; every service mutation and patient read calls can(); proxy.ts only does the optimistic cookie redirect (per the Next 16 auth guide)
- (decision) Mutations: Server Actions only for UI writes; each action validates with Zod, checks can(), then calls one module service method that runs in one DB transaction and writes its audit_log row in that same transaction
- (decision) Queue concurrency: issue number and Call next run in BEGIN IMMEDIATE transactions; queue_counters(facility_id, opd_date, last_seq) row per facility per day; UNIQUE(facility_id, opd_date, seq) on queue_entries
- (decision) Queue group is computed once at entry creation and stored on the entry (sort_group, urgency_rank, priority_category, entered_at); ordering = sort_group, urgency_rank, entered_at. Settings changes do not re-sort existing entries (FR-24)
- (decision) Time: store UTC ISO-8601 text; the OPD day is the Asia/Manila calendar date computed by one helper (opdDate()); all day logic (numbering, reset, closing) uses it
- (decision) Live updates: TanStack Query 5.104 polling (refetchInterval 3s) on queue views and the Display Board against read-only route handlers; mutations via useMutation calling Server Actions with invalidation. SSE deferred
- (decision) Display Board: separate (display) route group with no app shell; access by a device token in an httpOnly cookie checked against display_devices; its API returns queue numbers and facility names only
- (decision) IDs: internal primary keys are text UUIDv7-style (crypto.randomUUID acceptable); Hospital Number HN-YYYY-NNNNNN issued from a counter table in the same transaction as patient creation
- (decision) Settings (facilities, urgency levels, priority categories, schedules, prenatal target) live in tables owned by the settings module, read through its service; never hard-coded constants
- (decision) Encryption at rest: OS/disk encryption (e.g. BitLocker) on the server volume holding the SQLite file and backups; TLS via reverse proxy for transit. SQLCipher deferred
- (decision) Backups: nightly VACUUM INTO to a dated file on a separate disk, 30 kept; restore procedure documented
- (decision) Testing: Vitest 5 for services against a temp-file SQLite migrated fresh per test file; required from the first story for queue ordering, numbering, permissions
- (assumption) Server OS and hardware unknown; spine stays OS-neutral except the encryption note
